I built a website that shows how pathfinding algorithms think.

Watching Dijkstra and A* search a maze, one grid at a time

React · Firebase Try it live ↗ GitHub ↗

Pathfinding Visualizer is a website that animates how different algorithms find the shortest path between two points on a grid. It's one of my earlier projects, which I built back in college in 2021.

If you've taken an algorithms class, you've probably seen Dijkstra's algorithm or A* search as pseudocode on a slide. The pseudocode is not that hard to read. What's harder is getting a feel for how each algorithm actually explores: which cells it looks at first, why one algorithm finishes faster than another, and why some of them don't always find the shortest path. So this website lets you just watch it happen.

How it works

The board is a 20 x 20 grid. Using it is pretty simple:

  1. Click on two grids to set the start and end points.

  2. Click twice on a grid to turn it into an obstacle, or use "Generate Maze" to build a whole maze for you.

  3. Pick an algorithm from "Run Pathfinding Algorithms", and watch it search.

While the algorithm runs, each grid changes color: orange for grids that were already explored, light orange for grids that are about to be explored, and green for the final shortest path.

The algorithms

There are 4 pathfinding algorithms to choose from:

  1. Breadth-First Search: unweighted, and guarantees the shortest path.

  2. Dijkstra's Algorithm: weighted, and guarantees the shortest path.

  3. A* Search: weighted, and guarantees the shortest path.

  4. Greedy Best-First Search: weighted, but does not guarantee the shortest path.

And 2 ways to generate a maze: Randomized Prim's Algorithm, or just a random maze.

Technical challenges

Turning a grid into a graph

All of these algorithms work on graphs, not grids. So the first step is to treat every grid as a node, and connect it to its neighbors. A natural question arises: how far apart are two neighbors?

For the weighted algorithms, I set the distance between a grid and its vertical or horizontal neighbor to be 1, and the distance to a diagonal neighbor to be 1.4 (roughly √2). That way, going diagonally is cheaper than going right and then down, which is how it works in real life too.

Giving A* a good guess

What makes A* faster than Dijkstra is the heuristic: an estimate of how far each grid still is from the target. For each grid, A* keeps track of two numbers, the cost from the start so far and the estimated cost to the end, and it always explores the grid with the smallest sum first.

I used the straight-line (Euclidean) distance to the target as the estimate. Since a straight line is never longer than the real path, the estimate never overshoots, so A* still finds the shortest path, while exploring a lot fewer grids than Dijkstra. When two grids have the same total, it picks the one closer to the target to break the tie.

Greedy Best-First Search only looks at the estimate and ignores the cost so far. That's why it's usually the fastest to reach the end, but the path it finds isn't always the shortest. It's actually a nice thing to see side by side with A*.

Animating the search

If you just run the algorithm normally, it finishes instantly and you only see the final result. That's not very useful for a visualizer. So instead of running the whole search in one loop, each algorithm runs one step at a time on a timer (setInterval). Every tick, it explores the next grid, updates the colors, and React re-renders the board. Once it reaches the target, it traces back and draws the shortest path in green.

Deployment

The website is a React app with React Bootstrap for the navigation bar and popups, hosted on Firebase Hosting. I also set up GitHub Actions, so every push automatically builds and deploys the site.

What I've learnt

Seeing an algorithm is different from reading it

I understood these algorithms on paper before this project, but building the visualizer made them click in a different way. For example, you can literally see Dijkstra spreading out in every direction like a circle, while A* heads straight toward the target. It's one thing to know that a heuristic helps, and another thing to watch it skip half the board.

The small details make it usable

The first version was just a grid and some buttons. Then I added a tutorial popup, a color legend, warning popups when you try to run an algorithm without picking two grids, and an "About Our Algorithms" page. None of these are hard to build, but without them, a first-time visitor wouldn't really know what to do.
